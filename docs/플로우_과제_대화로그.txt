플로우 엔터프라이즈 개발자 지원 과제 — 대화 및 진행 로그
기록 시작일: 2026-10-23 (한국 시간)
기록 범위: 사용자가 로그 작성을 요청한 현재 대화부터.
정확한 개별 메시지 시각은 제공되지 않아 날짜와 순서로 기록한다.
기록 방식: 사용자 질문 원문, 공개 답변, 실제 수행 과정, 확인 사실, 제안, 미수행 항목을 구분한다.
이 대화의 후속 응답 때 동일 파일에 누적한다. 대화 밖에서 자동 감시하거나 다른 대화를 자동 수집하는 기능은 설정하지 않았다.
내부 추론, 인증정보, 임시 다운로드 주소는 기록하지 않는다.

[001 / 사용자 질문 원문]
플로우 회사와 내가 지원한 엔터프라이즈 개발자 직군이 어떤일을 하는지 와 어떤 기술 스택을 사용하는지 캡처이미지를 참고해서 조사해줘.  
이를 바탕으로 과제지시사항.md를 수행할 예정이야. 
핵심 사항을 1줄로 요약해줘 

참고로 이번 섹션에서 내가 질문하고 너가 답변을 준 내용과 진행 과정을 로그로 볼 수 있는 텍스트 파일을 하나 만들어서 현재 대화부터 계속 로그를 업데이트해줘.

[003 / 어시스턴트 진행 안내 1]
첨부한 채용 화면과 과제 파일을 확인한 뒤, 플로우 회사와 엔터프라이즈 개발 직무를 조사하겠습니다. 대화 기록 파일은 Library 스킬을 사용해 만들고, 이번 대화의 질문·답변·진행 내용을 이어서 기록하겠습니다.

[004 / 실제 수행 과정]
1. 파일 접근과 저장에 필요한 Library 스킬을 읽었다.
2. 첨부 과제 전체 155줄을 읽었다.
3. 이미지 읽기를 요청했으나 텍스트 추출 결과가 불명확했다.
4. 이미지를 내려받아 확대 확인하려 했으나 로컬 네트워크 이름 해석 실패로 다운로드가 실패했다. 캡처를 정밀하게 읽었다고 판단하지 않았다.
5. 웹 검색으로 마드라스체크·플로우 엔터프라이즈 개발 직무를 찾았다.
6. 검색 결과에는 공고 시기별로 다른 요구 기술이 있어 공식 회사 홈페이지의 해당 직무 페이지를 추가로 확인했다.
7. 공식 제품 소개, 구축·운영방법론, 엔터프라이즈 직무 페이지를 열어 교차 확인했다.
8. 확인 사실과 과제 분석을 아래에 기록하고 텍스트 파일을 작성했다.

[005 / 어시스턴트 진행 안내 2]
과제 파일은 “실제로 업로드를 차단하는 기능”과 “판단 근거·AI 활용 기록”을 중요하게 평가합니다. 채용공고에서는 플로우 기능 개발, 고객사 시스템 연동, 구축 후 운영 대응을 확인했습니다. 첨부 화면의 기술 목록도 대조하고 있습니다.

[006 / 조사 결과 — 확인 사실]
회사와 제품:
- 회사명은 마드라스체크(주), 플로우는 협업 서비스명이다.
- 공식 사이트는 협업·소통, 메신저, 업무일정관리, 지식·문서관리, AI 에이전트 등의 기능을 소개한다.
- 구독형 서비스와 고객사 서버에 설치하는 구축형 제품이 있다.
- 공식 주소는 서울 영등포구 영신로 220, KnK디지털타워 14층으로 표기되어 있다.

직무:
- 플로우 신규 기능 개발과 유지운영.
- 표준 API 개발. API(Application Programming Interface)는 프로그램끼리 기능과 데이터를 주고받는 접점이다.
- 고객사 내부 시스템과 플로우 연동.
- 고객사의 기술·개발·운영 문제 대응.
- 공식 구축방법론은 요구사항 파악, 서버·데이터베이스·네트워크 설계, 인사·조직도와 계정 연동, 통합시험, 보안 점검, 오픈 및 안정화, 유지보수를 설명한다.
- SSO(Single Sign-On)는 한 번 로그인해 여러 서비스를 이용하는 방식이다.
- AD(Active Directory)는 조직의 계정과 자원 등을 관리하는 디렉터리 서비스다.

공식 직무 페이지의 필요 스킬:
- Java / JavaScript / jQuery / Node.js / RDB.
- Docker / Linux.
- Git.
- AWS(Amazon Web Services).
- RDB(Relational Database)는 관계형 데이터베이스이며, 데이터를 서로 연결된 표로 관리한다.

공식 직무 페이지의 우대 항목:
- 대용량 데이터베이스 조회, 인덱스, 비용 튜닝에 대한 관심.
- JavaScript 모듈 기반 화면 구현에 대한 관심.
- 웹서버·애플리케이션 서버·데이터베이스 이중화 및 리버스 프록시.
- Node, Apache, Nginx, Tomcat, PostgreSQL.
- Prometheus / Grafana / Scouter 모니터링.
- JMeter 성능시험.
- 이들은 요구·우대 기술이며 모든 기술의 실제 운영 범위나 버전은 확인하지 않았다.

공고 간 차이와 유의점:
- 공식 직무 페이지에는 상단 '경력 무관'과 필요 스킬의 '관련 경력 3년 이상'이 함께 표기되어 있어 모순이 있다. 지원 자격을 단정하지 않는다.
- 원티드의 별도 신입 공고는 마감일이 2026-06-30으로 표기되어 있어 현재 지원한 공고와 동일한 것으로 간주하지 않는다.
- 검색된 다른 공고 요약에는 Spring/NestJS 등이 등장하지만, 확인한 공식 Enterprise 직무의 필수 프레임워크로 단정하지 않는다.
- React, Next.js, Python, 특정 AI 모델은 이 공식 직무 페이지에서 확인하지 않았다.

[007 / 과제 파일 분석 — 필수 요건]
목적:
- 확장자 차단 정책을 관리하고 실제 파일 업로드에 강제 적용하는 작은 서비스를 배포한다.
- 구현 이유, 보안·예외·운영 판단과 AI 활용 과정을 문서화한다.

고정 확장자:
- bat, cmd, com, cpl, exe, scr, js.
- 초기값은 모두 미선택.
- 선택/해제 결과를 데이터베이스에 저장하고 새로고침 후 유지.
- 고정 확장자를 커스텀 목록에 표시하지 않는다.

커스텀 확장자:
- 입력 최대 20자.
- 최대 200개.
- 추가 후 데이터베이스 저장과 목록 표시.
- 삭제 버튼으로 데이터베이스에서 삭제.
- 중복 추가 방지.

실제 업로드:
- 서버에서 저장된 정책을 적용.
- 차단 시 명확한 이유 안내.
- 정상 파일은 실제 저장 및 성공 처리.
- 정책 관리 화면만 구현하면 최소 범위를 충족하지 못한다.

제출:
- GitHub 저장소: 스키마와 실행 방법 포함.
- 누구나 접속할 수 있는 배포 주소: 면접 당일 실제 호출 가능.
- CONSIDERATIONS.md: 고려사항과 판단 근거.
- PROMPT_LOG.md 등: AI 입력 기록, 사용한 스킬·플러그인·도구, 결과를 수용·수정·폐기한 이유.

해석:
- 과제의 AI 활용은 개발 과정의 AI 사용과 검증 기록을 뜻한다.
- 업로드 서비스에 AI 모델이나 챗봇 기능을 넣으라는 필수 요건은 없다.
- 기술 스택은 자유다.
- 현재 로그는 조사 단계 기록이며 구현·시험 증빙을 대신하지 않는다.

[008 / 과제와 직무의 연결 — 분석 의견]
- 정책의 데이터베이스 저장과 업로드 검증의 일치는 고객사 정책을 실제 서비스에 적용하는 역량과 연결된다.
- 화면·API·저장소를 끝까지 연결하는 구현은 웹·서버 개발 업무와 연결된다.
- 오류 처리, 로그, 동시 편집, 배포 및 재시작 후 유지 여부는 운영 대응 역량을 보여줄 수 있다.
- 이는 공식 직무와 과제를 함께 읽고 도출한 분석이며 회사의 비공개 평가 기준을 확인한 것은 아니다.
- 특정 기술을 많이 넣는 것보다 필수 동작과 판단 근거를 설명할 수 있는 범위로 완성하는 방향이 과제 안내와 부합한다.

[009 / 이후 검토할 항목 — 아직 미구현·미검증]
- 대소문자, 이중 확장자, 확장자 없는 파일, 숨김 파일의 처리 기준.
- 확장자와 MIME(Multipurpose Internet Mail Extensions) 유형·실제 파일 내용의 불일치.
- 파일 크기 및 개수 제한.
- 원본 파일명을 저장 경로로 사용하지 않도록 하는 방안.
- 고정/커스텀 확장자 충돌 기준.
- 데이터베이스 중복 제약과 200개 제한의 동시 요청 정합성.
- 저장 실패 시 화면과 데이터베이스 상태 일치.
- 정책 수정 권한, 공개 데모의 데이터 초기화·보관 기간.
- 배포 환경의 파일 저장 지속성과 서버 재시작 후 설정 유지.
- 구현 여부와 제외 이유는 개발 단계에서 결정해야 하며 이 로그에서 결정 완료로 취급하지 않는다.

[010 / 사용 스킬·도구와 목적]
- Library 스킬 및 파일 도구: 제공 파일 읽기와 대화 로그 파일 생성·저장.
- 웹 검색·페이지 열기: 회사 공식 제품·직무·구축 방법론 확인.
- 파일 편집 도구: UTF-8 텍스트 로그 작성.
- PowerShell / Python: 이미지 다운로드와 파일 작업 시도. 이미지 다운로드는 이름 해석 오류로 실패.
- Node.js 실행 도구: 작업 환경 경로 확인.
- 이번 조사에서는 개발용 하위 에이전트나 별도 멀티에이전트 작업을 사용하지 않았다.
- 과제용 애플리케이션 코드를 생성하거나 테스트하지 않았다.

**네, 가능합니다. 필수 기능을 먼저 시험하고, 그 결과를 근거로 DEC를 결정하는 순서가 좋습니다.** DEC는 이 가이드에서 설계 결정(Decision)을 구분하는 번호입니다.

다만 시험 종류를 나누면 됩니다.

| 구분 | 예시 | 진행 방법 |
|---|---|---|
| 과제에 정답이 정해진 시험 | 최초 7종 미선택, 저장 유지, 20자·200개 제한, 삭제, 실제 차단 | 최소 기능을 구현한 뒤 먼저 확인 |

| 결정한 정책의 검증 시험 | 확정한 크기 제한·파일명 처리·충돌 처리 | DEC 확정 후 다시 시험해 통과 여부 판정 |

예를 들어 **파일 크기를 임시로 10 MiB로 설정해 경계값을 시험**할 수 있습니다. 이때 결과는 “10 MiB가 최선”이 아니라 “이 임시 설정에서 이렇게 동작했다”입니다. 운영 환경과 사용 목적까지 보고 최종 제한을 정하면 됩니다.

추천 순서는 다음과 같습니다.

1. **필수 기능의 최소 구현**
2. **필수 조건 시험**
3. **미확정 정책의 탐색 시험과 결과 기록**
4. **DEC별 선택·이유·제외한 대안 확정**
5. **확정 기준으로 재시험**

현재는 앱이 구현되지 않았으므로, 먼저 시험할 작은 기능을 만들어야 합니다. 첫 묶음은 **T01~T04: 최초 상태 → 선택 저장 → 재시작 유지 → 커스텀 추가**가 적합합니다.
