정책 변경과 감사 기록 흐름

입력·버전·대상 오류는 트랜잭션 성공 전에 4xx로 거부합니다. 최신 버전으로 이미 삭제한 ID를 다시 삭제하면 404이며 버전·감사는 늘지 않습니다.

응답이 끊긴 업로드 결과 조회 흐름

정상 POST 응답이 READY면 바로 완료합니다. 명확한 입력 오류는 사용자가 수정할 수 있게 안내합니다. 타임아웃·전송 오류·5xx·중복 요청 번호는 조회로 확인합니다.

헷갈리기 쉬운 세 가지 번호

이름역할
업로드 조회 requestId클라이언트가 POST 전에 만든 UUID. X-Upload-Request-Id → upload_record.request_id → GET status의 조회 키.
파일 id서버가 만든 파일 식별자. upload_record.id와 UUID.bin이 같은 UUID로 대응하며 물리 파일 경로는 응답하지 않음.
오류 error.requestId서버 오류 추적 번호. 미확인 업로드의 조회 번호와 다른 역할이며 서로 바꾸어 쓰지 않음.

DB에 무엇이 남나요?

저장 위치의미
policy_scope + extension_policy현재 정책 버전과 고정/커스텀 규칙
policy_change정책 FK·변경 후 버전·동작·확장자·enabled·시각, 정책별 버전 UNIQUE
upload_record.request_id조회용 UUID UNIQUE. 기존 행은 id로 채우며 파일 ID와 본문은 그대로 유지

policy_change.policy_id는 실제 FK입니다. policy_version은 당시 버전의 숫자 기록이며 현재 버전으로 연결한 FK가 아닙니다. 파일 본문은 UUID.bin으로 별도 저장합니다. 자세한 ERD는 MD 보고서에 있습니다.

구현 범위와 확인할 한계

  • 404 조회 없음은 아직 처리 중·미도착·저장 실패를 구별하지 못합니다. 자동 재전송하거나 실패로 확정하지 않습니다. 미확인 요청을 닫고 새 파일을 보내는 것은 사용자의 명시적 선택입니다.
  • sessionStorage는 같은 탭의 새로고침 복원을 위한 저장 공간입니다. 저장 차단이나 탭 종료 후의 번호 복원은 보장하지 않습니다.
  • policy_change.policy_id는 policy_scope.id를 참조하는 실제 FK입니다. policy_version은 당시 숫자 기록입니다. 업로드 policy_version은 현재 정책 버전의 FK가 아니고 파일 본문도 DB FK로 연결되지 않습니다.
  • 감사 기록은 PR3부터 남기며 과거 변경·인증되지 않은 사용자 주체를 지어내어 채우지 않습니다. V3는 기존 업로드 request_id를 id로 백필하지만 파일 ID·본문은 바꾸지 않습니다.
  • DB와 디스크는 하나의 원자적 트랜잭션이 아닙니다. 알려진 롤백 파일 정리는 유지하며 강제 종료·커밋 결과 불명·정리 실패는 DB/파일 수동 대조 대상입니다.
  • 실제 Nginx 단독 검사는 전체 앱 이미지 빌드·Compose 기동·컨테이너 재생성·공개 배포 검증과 구분합니다. 인증·공개 격리·보관/총량 정책·악성코드 검사는 이번 범위에 포함하지 않았습니다.
  • 이 보고서는 PR3 최종 소스와 기존 CI 로그를 확인한 문서입니다. 문서 작성 중 새로 실행한 앱 시험으로 표기하지 않았습니다.
